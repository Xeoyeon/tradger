# 04. 출시 전 베타 배포와 사전 홍보

> 앱스토어에 정식으로 출시하기 전에 사람들에게 앱을 알리고, 실제로 써 보게 하는 방법을 정리한다.
> 배포·심사 요건은 [03 문서 4장](03-tech-stack-review.md#4-실제-배포-준비)을 따른다.

## 0. 요약

- 정식 출시 전에도 실제 사람에게 앱을 쓰게 할 수 있다. **iOS는 TestFlight, Android는 Google Play 비공개 테스트**다.
- Android 베타는 선택이 아니라 **필수 과정**이다. 새 개인 계정은 테스터 12명이 14일 연속 참여해야 정식 출시를 신청할 수 있다. 베타 운영이 곧 출시 조건 충족이다.
- 홍보 순서: **대기자 명단 페이지 → 베타 테스터 모집 → 사전 예약 → 정식 출시**.
- 이 앱의 가치는 해외여행 중에 드러난다. 테스터는 **곧 해외여행을 가는 사람**으로 모은다.

---

## 1. 단계별 배포 방법

| 단계 | 대상 | iOS | Android | 심사 |
|---|---|---|---|---|
| **① 지인 테스트** (기능 일부 완성) | 5~10명 | EAS 내부 배포(ad hoc). 기기를 개발자 계정에 등록해야 하고 1년에 iPhone 100대까지 | EAS 내부 배포 APK 링크. 링크만 보내면 설치된다 | 없음 |
| **② 클로즈드 베타** (MVP 완성) | 20~50명 | **TestFlight 외부 테스트**. 이메일 또는 **공개 링크**로 최대 10,000명. 첫 빌드만 TestFlight 심사 | **Play 비공개 테스트**. 이메일 목록이나 Google 그룹으로 초대. **12명 이상이 14일 연속 참여하면 정식 출시 신청 가능** | iOS 첫 빌드만 |
| **③ 사전 예약** | 일반 사용자 | **App Store 사전 주문**. 출시일을 2~180일 뒤로 잡고 미리 공개 | **Play 사전 등록**. 정식 출시 권한을 받은 뒤 열 수 있다 | 스토어 심사 |
| **④ 정식 출시** | 전체 | App Store | Play 프로덕션 (단계적 출시) | 스토어 심사 |

**운영 팁**
- Android 테스터는 **15~20명**을 모은다. 한 명이라도 14일 안에 빠지면 카운트가 처음부터 다시 시작된다.
- 베타 기간의 버그 수정은 EAS Update `preview` 채널로 바로 보낸다. 테스터가 앱을 다시 설치할 필요가 없다.
- TestFlight 빌드는 올린 지 90일이 지나면 만료된다. 베타가 길어지면 새 빌드를 올린다.
- 공개 링크는 아무나 들어올 수 있다. 인원을 조절하려면 TestFlight 공개 링크의 최대 인원을 설정한다.

## 2. 일정 예시

| 시점 | 할 일 |
|---|---|
| 출시 8주 전 | 대기자 명단 페이지 오픈. 커뮤니티에 개발 과정 공유 시작 |
| 6주 전 | ① 지인 테스트. 치명적인 버그와 입력 흐름 점검 |
| 4주 전 | ② 클로즈드 베타 시작. **Android 14일 카운트 시작** |
| 2주 전 | Play 정식 출시 권한 신청 (14일 충족 후). App Store 심사 제출, 사전 주문·사전 등록 오픈 |
| 출시일 | 정식 출시. 대기자 명단과 베타 테스터에게 알림 |

정식 출시 권한 신청과 스토어 심사에는 며칠씩 걸릴 수 있으므로, 출시일 앞에 1주 정도 여유를 둔다.

## 3. 사전 홍보

### 3.1 대기자 명단 페이지

한 페이지면 충분하다.

- **문제**: "해외여행 다녀오면 원화로 얼마 썼는지 모르겠다", "환전한 돈이랑 카드값이 섞여서 계산이 안 된다"
- **해결**: 환전 한 번 기록하면 달러로만 적어도 원화가 자동 계산. 카드 결제는 추정 후 청구액으로 확정.
- **화면**: 스크린샷이나 15초 영상
- **신청 폼**: 이메일, iOS/Android, **다음 해외여행 일정과 나라**
  - 여행 일정을 받아 두면 여행 직전에 초대할 수 있다. 실제로 쓰고 피드백을 줄 가능성이 가장 높은 시점이다.
- **도구**: 노션 페이지 + 구글 폼(또는 Tally)으로 시작해도 된다.
- **개인정보**: 이메일을 받으므로 수집·이용 동의(목적, 항목, 보유 기간)를 폼에 표시한다.

### 3.2 모집 채널

| 채널 | 이유 | 방법 |
|---|---|---|
| 여행 커뮤니티 (네이버 여행 카페, 국가·지역별 카페) | 여행 직전이거나 여행 중인 사람이 많다 | 게시판 홍보 규정을 확인하고, "여행 가계부 직접 만들어 봤다" 같은 개발 후기 형식으로 |
| 카드·환율 커뮤니티 | 트래블카드, 환율 우대에 민감한 사람들. 핵심 타깃 | "트래블카드 결제 원화로 정확히 계산하기" 같은 팁과 함께 소개 |
| 메이커 커뮤니티 (디스콰이엇 등) | 초기 제품에 피드백을 주는 문화가 있다 | 개발 과정 공유, 베타 모집 |
| 인스타그램, 스레드 | 여행 콘텐츠를 많이 본다 | 실제 여행 가계부 화면, 짧은 영상 |
| 대학 커뮤니티 | 방학 해외여행, 교환학생 | 방학 직전 시즌에 |
| 지인, 오픈채팅 | Android 테스터 12명을 가장 빨리 확보하는 방법 | 베타 전용 오픈채팅방을 만들어 피드백 창구로도 쓴다 |

광고 글을 금지하는 게시판이 많다. 커뮤니티마다 규정을 먼저 확인한다.

### 3.3 피드백 수집

- **TestFlight 내장 피드백**: 테스터가 스크린샷과 함께 바로 보낼 수 있다.
- **앱 안 "의견 보내기" 버튼**: Android 테스터용.
- **베타 오픈채팅방**: 빠른 질문과 답.
- **Sentry**: 오류는 자동으로 수집된다.
- **여행 후 설문 (3~5문항)**: 가장 중요한 질문은 **"앱의 원화 합계가 실제 통장·카드 청구액과 맞았나요?"** 이다. 이 앱의 핵심인 정확성을 실제 데이터로 검증할 수 있다.

## 4. 베타에서 주의할 점

| 항목 | 내용 |
|---|---|
| **베타 데이터 유지** | 베타 테스터도 실제 돈을 기록한다. TestFlight → App Store, Play 테스트 → 프로덕션은 같은 앱이라 데이터가 유지된다. 하지만 **EAS로 직접 받은 Android APK는 Play 버전과 서명이 달라 덮어쓸 수 없다.** 지우고 다시 설치해야 해서 데이터가 사라진다. 그래서 ①단계 빌드부터 **백업 파일 기능**(02 문서 D5)을 넣고, 넘어가기 전에 백업을 안내한다 |
| 스토어 정보 | 앱 설명, 스크린샷, 개인정보처리방침은 베타 때 만들어 두면 정식 출시 때 그대로 쓴다 |
| 서버 | 베타 기간은 Supabase 무료 플랜으로 충분하다. 정식 출시부터 Pro (03 문서 4.4) |
| 계산 버그 | 돈 계산 버그가 나오면 EAS Update로 즉시 수정하고, 영향받은 기록이 다시 계산되는지 확인한다 |
